# lavka

Бэкенд онлайн-магазина продуктов на Java 21 и Spring Boot 4:

- **авторизация** по email и паролю на JWT-токенах;
- **каталог товаров** с остатками на складе;
- **заказы** с позициями по зафиксированной цене, списанием со склада и историей статусов.

Подтверждения почты, ролей, сессий, смены пароля, корзины и Redis пока нет: их сделаем в следующих итерациях.

## Запуск

```bash
cp .env.example .env              # затем вставить ключ: openssl rand -base64 48
docker compose up -d              # Postgres на localhost:5432
./mvnw spring-boot:run            # приложение на http://localhost:8080
```

- **Docker Desktop должен быть запущен** до `docker compose up` и до запуска приложения. Иначе приложение падает при старте с `Connection to localhost:5432 refused`: базы нет, и Liquibase не может к ней подключиться. После перезагрузки компьютера: запустить Docker Desktop → `docker compose up -d` → приложение. Данные лежат в volume `postgres-data` и переживают перезапуски.

- **`.env`** хранит `JWT_SECRET`, ключ подписи токенов длиной не меньше 32 байт. Файл не коммитится. Без него приложение не стартует.
- **Схему БД** создаёт Liquibase при старте приложения (`src/main/resources/db/changelog`).
- **Тесты** (`./mvnw test`) поднимают свой Postgres через Testcontainers, поэтому нужен запущенный Docker. Локальная база тестами не затрагивается. Подробнее — в разделе [Тесты](#тесты).
- **Lombok.** В IntelliJ нужен плагин Lombok (в новых версиях встроен) и включённая галочка *Settings → Build → Compiler → Annotation Processors → Enable annotation processing*. После изменения `pom.xml` — *Reload Maven Project*. Версия Lombok закреплена в `pom.xml` (`1.18.48`): версия 1.18.46, которую подтягивает Spring Boot, роняет компилятор на JDK 27 (`ExceptionInInitializerError: EndPosTable`).

**Swagger UI** — http://localhost:8080/swagger-ui/index.html. Он показывает спецификацию `src/main/resources/static/openapi.yaml` (OpenAPI 3.1, написана вручную: описания, все коды ошибок, примеры). Чтобы отправить запрос к закрытой ручке, нажмите **Authorize** и вставьте `access_token` без слова `Bearer`. Спецификация, сгенерированная из кода (springdoc), лежит на `/v3/api-docs`. Если меняете ручки, обновляйте и `openapi.yaml`.

Сценарий для IntelliJ HTTP Client лежит в `src/test/api.http`: 40 запросов ко всем ручкам, каждый проверяет свой ответ. Выберите окружение `dev` (`src/test/http-client.env.json`) и нажмите **Run All Requests in File**. Запросы передают друг другу токены и `id`, email каждый раз новый, поэтому файл можно запускать сколько угодно раз. Каждый запуск оставляет в локальной базе тестового пользователя, два товара и отменённый заказ.

## Как устроен код

```
demo.lavka
├── controller   HTTP: принимает запрос, проверяет тело (@Valid), выбирает код ответа
├── service      бизнес-логика и транзакции: проверки, 404/409, склад, логирование
├── repository   Spring Data JPA: запросы к базе
├── entity       JPA-сущности, один к одному с таблицами
├── model        DTO: тела запросов и ответов
├── auth         JWT, пароли, проверка токенов
└── config       настройки (ключ JWT, BCrypt)
```

Запрос проходит слои по порядку: `Controller → Service → Repository → база`.

- **Наружу отдаются только DTO** (`ProductResponse`, `OrderResponse`, `UserResponse` и т. д.), а не JPA-сущности. Так в ответ не попадёт лишнее, например хеш пароля, и не сработает случайно ленивая загрузка связей.
- **Транзакции на сервисе.** В `application.yaml` стоит `spring.jpa.open-in-view: false`, поэтому сессия Hibernate живёт только внутри `@Transactional`-метода сервиса. Это важно в двух случаях:
  - метод меняет сущность и не вызывает `save()`. Изменения записывает dirty checking при коммите, а он работает, только пока сущность **managed** (прикреплена к открытой сессии). Без транзакции сущность сразу становится **detached**, и изменения молча теряются;
  - метод обращается к ленивым (`LAZY`) связям. Вне транзакции это `LazyInitializationException`.

  Чтение помечено `@Transactional(readOnly = true)`: Hibernate не хранит снимки сущностей и не проверяет их на изменения.
- **Проверка данных в трёх местах:** Bean Validation на DTO в контроллере (клиент получает понятный `400`), проверки в сервисе (страховка для вызовов не из контроллера) и `CHECK`, `NOT NULL`, внешние ключи в базе (последняя линия защиты).
- **Схема только через Liquibase.** Hibernate работает в режиме `ddl-auto: validate`: он сверяет сущности с таблицами и не даёт приложению стартовать, если они разошлись. Применённые changeset'ы не меняют, для изменений пишут новый файл в `db/changelog/changes`.
- **Lombok на сущностях** — только `@Getter`, `@Setter` на изменяемых полях, `@Builder` и `@NoArgsConstructor(access = PROTECTED)` для JPA. `@Data`, `@EqualsAndHashCode` и `@ToString` на сущностях не используем: они обращаются ко всем полям, включая ленивые связи. Это `LazyInitializationException`, лишние запросы или бесконечная рекурсия в `toString` при двусторонних связях, а `hashCode` меняется после `persist`, когда появляется `id`.
- **Позиции и история — часть заказа.** `OrderItem` и `OrderStatusHistory` создаются только через методы `Orders` (`addItem`, `changeStatus`) и сохраняются вместе с заказом через `cascade`. Поэтому сменить статус мимо истории нельзя.

## Как устроены токены

После регистрации и логина клиент получает пару токенов:

```json
{
  "access_token":  "eyJhbGciOiJIUzUxMiJ9...",
  "refresh_token": "eyJhbGciOiJIUzUxMiJ9..."
}
```

| | access_token | refresh_token |
|---|---|---|
| Для чего | передаётся с каждым запросом в `Authorization: Bearer <token>` | только чтобы получить новую пару в `POST /auth/refresh` |
| Срок жизни | 15 минут (`auth.jwt.access-ttl`) | 30 дней (`auth.jwt.refresh-ttl`) |
| Внутри | `sub` = id пользователя, `typ` = `access` | `sub` = id пользователя, `typ` = `refresh` |

- Оба токена — JWT, подписанные ключом из `.env`. Подделать их нельзя, но прочитать содержимое может кто угодно. Поэтому в токен не кладём ничего секретного.
- Поле `typ` не даёт использовать refresh-токен вместо access-токена и наоборот.
- Все проверки токена собраны в одном методе `JWTService.validateToken(token, expectedType)`. Он проверяет по порядку:
  1. **подпись**: jjwt пересчитывает HMAC от `header.payload` нашим ключом и сравнивает с подписью токена;
  2. **срок**: `exp` не в прошлом;
  3. **тип**: `typ` совпадает с ожидаемым (`access` или `refresh`);
  4. **отзыв**: токен не отозван через logout или refresh.

  На первой же неудаче метод бросает `InvalidTokenException` с причиной (`BAD_SIGNATURE`, `EXPIRED`, `WRONG_TYPE`, `REVOKED`, `MALFORMED`), и клиент получает `401`.
- Отозванные токены (после выхода или обмена refresh-токена) хранятся в памяти приложения до окончания своего срока. **После перезапуска приложения этот список очищается.**

## Таблица `users`

| Колонка | Тип | |
|---|---|---|
| `id` | `BIGSERIAL` | первичный ключ |
| `email` | `VARCHAR(254)` | уникальный, хранится в нижнем регистре |
| `password_hash` | `VARCHAR(100)` | BCrypt-хеш, сам пароль нигде не хранится |
| `created_at` | `TIMESTAMPTZ` | когда создан |
| `updated_at` | `TIMESTAMPTZ` | когда обновлён |

## Таблица `products`

| Колонка | Тип | |
|---|---|---|
| `id` | `SERIAL` | первичный ключ |
| `name` | `VARCHAR(255)` | название товара |
| `quantity` | `INTEGER` | сколько штук на складе, по умолчанию `0`, не может быть меньше нуля |
| `price` | `NUMERIC(10, 2)` | цена с копейками, не может быть меньше нуля |

## Таблица `orders`

| Колонка | Тип | |
|---|---|---|
| `id` | `BIGSERIAL` | первичный ключ |
| `user_id` | `BIGINT` | чей заказ, ссылка на `users.id`. Пользователя с заказами удалить нельзя |
| `status` | `VARCHAR(20)` | статус заказа, по умолчанию `CREATED` |
| `created_at` | `TIMESTAMPTZ` | когда оформлен |
| `completed_at` | `TIMESTAMPTZ` | когда выполнен; заполнен только у заказов в статусе `COMPLETED` |

Статусы:

| Статус | Значение |
|---|---|
| `CREATED` | заказ оформлен |
| `PROCESSING` | заказ собирается |
| `READY` | заказ собран |
| `COMPLETED` | заказ выполнен / доставлен |
| `CANCELLED` | заказ отменён |

## Таблица `order_items`

Позиции заказа: какой товар, сколько и по какой цене.

| Колонка | Тип | |
|---|---|---|
| `id` | `BIGSERIAL` | первичный ключ |
| `order_id` | `BIGINT` | ссылка на `orders.id`. Позиции удаляются вместе с заказом |
| `product_id` | `INTEGER` | ссылка на `products.id`. Товар, который есть хоть в одном заказе, удалить нельзя |
| `quantity` | `INTEGER` | сколько штук, больше нуля |
| `price` | `NUMERIC(10, 2)` | цена за штуку **на момент заказа**. Если товар потом подорожает, старый заказ не изменится |

Один товар встречается в заказе не больше одного раза: `UNIQUE (order_id, product_id)`.

## Таблица `order_status_history`

Каждая смена статуса заказа: кто, когда, из какого статуса и в какой. Строки только добавляются и никогда не меняются.

| Колонка | Тип | |
|---|---|---|
| `id` | `BIGSERIAL` | первичный ключ |
| `order_id` | `BIGINT` | ссылка на `orders.id`. История удаляется вместе с заказом |
| `from_status` | `VARCHAR(20)` | прежний статус; `NULL` только у первой записи, когда заказ создан |
| `to_status` | `VARCHAR(20)` | новый статус |
| `changed_at` | `TIMESTAMPTZ` | когда изменён |
| `changed_by` | `BIGINT` | кто изменил, ссылка на `users.id`; `NULL` оставлен для изменений, которые сделает система |

База не даёт записать неизвестный статус или переход в тот же самый статус.

## Как связаны таблицы

```
users ──< orders ──< order_items >── products
              │
              └──< order_status_history
```

- `products.price` — **текущая** цена товара, её можно менять.
- `order_items.price` — копия цены **на момент заказа**, а сам момент заказа — `orders.created_at`.
- По `order_items.product_id` находится товар в `products`, оттуда берётся, например, его название.
- `products.quantity` — остаток на складе. Заказ уменьшает его, отмена заказа возвращает обратно.

## Ручки

### Регистрация — `POST /auth/register`

Создаёт пользователя и сразу выдаёт пару токенов, так что отдельно логиниться не нужно.

**Запрос:**
```http
POST /auth/register
Content-Type: application/json

{
  "email": "anton@example.com",
  "password": "123456"
}
```

**Как работает:**
1. Проверяет тело: `email` должен быть корректным адресом длиной до 254 символов, `password` — от 6 до 100 символов.
2. Приводит email к нижнему регистру и обрезает пробелы, поэтому `Anton@Example.com` и `anton@example.com` — один и тот же пользователь.
3. Если такой email уже есть, возвращает `409`.
4. Хеширует пароль через BCrypt и сохраняет пользователя в `users`.
5. Выдаёт пару токенов.

**Ответ `201 Created`:**
```json
{ "access_token": "...", "refresh_token": "..." }
```

| Код | Когда |
|---|---|
| `201` | пользователь создан |
| `400` | неверный email, пароль короче 6 символов или не хватает полей |
| `409` | `User already exists`: такой email уже зарегистрирован |

### Логин — `POST /auth/login`

Вход только по email и паролю.

**Запрос:**
```http
POST /auth/login
Content-Type: application/json

{
  "email": "anton@example.com",
  "password": "123456"
}
```

**Как работает:**
1. Находит пользователя по email без учёта регистра.
2. Сверяет пароль с хешем из базы через `BCrypt.matches`.
3. Выдаёт новую пару токенов. Каждый логин даёт отдельную пару, поэтому можно войти с нескольких устройств одновременно.

**Ответ `200 OK`:**
```json
{ "access_token": "...", "refresh_token": "..." }
```

| Код | Когда |
|---|---|
| `200` | вход выполнен |
| `400` | пустой email или пароль |
| `401` | `Invalid email or password`: такого email нет или пароль неверный. Ответ одинаковый в обоих случаях, чтобы по нему нельзя было узнать, зарегистрирован ли email |

### Выход — `POST /auth/logout`

Отзывает оба токена пары: и access, и refresh.

**Запрос:**
```http
POST /auth/logout
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "refresh_token": "<refresh_token>"
}
```

**Как работает:**
1. Проверяет refresh-токен из тела: подпись, срок действия, `typ = refresh`, токен не отозван.
2. Проверяет access-токен из заголовка так же, но **истёкший срок допускается**: access живёт 15 минут, и выйти нужно уметь и позже. Он должен принадлежать **тому же** пользователю.
3. Добавляет оба токена в список отозванных, сначала refresh.

Остальные логины этого пользователя, например на другом устройстве, продолжают работать.

**Ответ `204 No Content`** — без тела.

| Код | Когда |
|---|---|
| `204` | выход выполнен |
| `400` | в теле нет `refresh_token` |
| `401` | `Missing bearer token`: нет заголовка. `Token expired`: истёк refresh-токен (истёкший access не мешает). `Invalid token`: токен подделан, отозван или не того типа. `Refresh token belongs to another user`: refresh-токен другого пользователя |

### Текущий пользователь — `GET /users/me`

Возвращает данные пользователя, которому принадлежит access-токен. Тело запроса не нужно.

**Запрос:**
```http
GET /users/me
Authorization: Bearer <access_token>
```

**Как работает:**
1. Берёт токен из заголовка `Authorization: Bearer ...`.
2. Проверяет, что это действующий и не отозванный access-токен.
3. Достаёт из токена id пользователя (`sub`) и загружает пользователя из базы.

**Ответ `200 OK`:**
```json
{
  "id": 1,
  "email": "anton@example.com",
  "created_at": "2026-10-20T18:02:52.773189Z",
  "updated_at": "2026-10-20T18:02:52.773189Z"
}
```

Хеш пароля в ответ не попадает.

| Код | Когда |
|---|---|
| `200` | данные пользователя |
| `401` | `Missing bearer token`: нет заголовка. `Token expired`: access-токен истёк, пора вызвать `/auth/refresh`. `Invalid token`: токен подделан, отозван или передан refresh вместо access. `User not found`: пользователь удалён |

### Обновление пары — `POST /auth/refresh`

Когда access-токен истёк, клиент меняет refresh-токен на новую пару без повторного ввода пароля.

```http
POST /auth/refresh
Content-Type: application/json

{
  "refresh_token": "<refresh_token>"
}
```

- Возвращает `200` и новую пару `{ "access_token", "refresh_token" }`.
- Старый refresh-токен сразу отзывается: каждый refresh-токен можно использовать только один раз.
- Возвращает `401`: `Token expired`, если refresh-токен истёк (нужен новый логин), или `Invalid token`, если он подделан, уже использован или вместо refresh передан access-токен.

## Товары — `/products`

Каталог товаров: просмотр, создание, изменение и удаление строк таблицы `products`.

> **Пока без авторизации.** Токен не нужен, создавать, менять и удалять товары может кто угодно. Позже запись закроем ролью администратора.

| Метод | Путь | Что делает | Успех |
|---|---|---|---|
| `GET` | `/products` | список всех товаров | `200` |
| `GET` | `/products/{id}` | один товар | `200` |
| `POST` | `/products` | создать товар | `201` |
| `PUT` | `/products/{id}` | заменить все поля товара | `200` |
| `DELETE` | `/products/{id}` | удалить товар | `204` |

Как запрос проходит через приложение:

```
ProductController  ──►  ProductService  ──►  ProductRepository  ──►  таблица products
  проверка тела           бизнес-проверки,       Spring Data JPA
  (@Valid), коды          транзакция, 404,
  ответов, Location       логирование
```

- Наружу всегда отдаётся `ProductResponse`, а не сама JPA-сущность `Products`.
- Правила для полей проверяются в трёх местах: тело запроса (Bean Validation в контроллере, ответ `400`), `ProductService.validate(...)` и `CHECK`-ограничения в базе. Последние два — страховка на случай, если товар создаёт не контроллер, а другой код.

### Тело товара

Одинаковое для создания и изменения:

```json
{
  "name": "Молоко 3,2%",
  "quantity": 10,
  "price": 89.90
}
```

| Поле | Правила |
|---|---|
| `name` | обязательное, не пустое и не из одних пробелов. Пробелы по краям обрезаются |
| `quantity` | обязательное, целое, `>= 0` |
| `price` | обязательное, `>= 0`, не больше двух знаков после запятой и не больше `99 999 999.99` (колонка `NUMERIC(10, 2)`) |

Цена хранится в `BigDecimal`, а не в `double`, поэтому копейки не теряются на округлении.

### Список — `GET /products`

Возвращает все товары, отсортированные по `id`. Если товаров нет, возвращает пустой массив `[]`.

**Ответ `200 OK`:**
```json
[
  { "id": 1, "name": "Молоко 3,2%", "quantity": 10, "price": 89.90 },
  { "id": 2, "name": "Хлеб",        "quantity": 5,  "price": 45.00 }
]
```

### Один товар — `GET /products/{id}`

**Ответ `200 OK`:**
```json
{ "id": 1, "name": "Молоко 3,2%", "quantity": 10, "price": 89.90 }
```

| Код | Когда |
|---|---|
| `200` | товар найден |
| `404` | `Product {id} not found` |

### Создание — `POST /products`

**Запрос:**
```http
POST /products
Content-Type: application/json

{
  "name": "Молоко 3,2%",
  "quantity": 10,
  "price": 89.90
}
```

**Как работает:**
1. Контроллер проверяет тело по правилам из таблицы выше. При ошибке возвращает `400`, до базы запрос не доходит.
2. Сервис обрезает пробелы в `name` и ещё раз проверяет значения.
3. Собирает сущность через `Products.builder()` и сохраняет её. `id` выдаёт база.
4. Возвращает созданный товар и его адрес в заголовке `Location`.

**Ответ `201 Created`:**
```http
Location: http://localhost:8080/products/1
```
```json
{ "id": 1, "name": "Молоко 3,2%", "quantity": 10, "price": 89.90 }
```

| Код | Когда |
|---|---|
| `201` | товар создан |
| `400` | не хватает поля, пустое `name`, отрицательные `quantity` или `price`, больше двух знаков в `price` |

### Изменение — `PUT /products/{id}`

Заменяет **все** поля товара сразу, поэтому в теле нужны все три поля, как при создании. Частичного обновления (`PATCH`) пока нет.

**Запрос:**
```http
PUT /products/1
Content-Type: application/json

{
  "name": "Молоко 2,5%",
  "quantity": 7,
  "price": 79.90
}
```

**Как работает:**
1. Проверяет тело так же, как при создании.
2. Загружает товар по `id`. Если его нет, возвращает `404`.
3. Меняет поля через сеттеры. Отдельный `save()` не вызывается: метод работает в транзакции (`@Transactional`), и при коммите Hibernate сам замечает изменённые поля и делает `UPDATE` (dirty checking).
4. Возвращает обновлённый товар.

**Ответ `200 OK`:**
```json
{ "id": 1, "name": "Молоко 2,5%", "quantity": 7, "price": 79.90 }
```

| Код | Когда |
|---|---|
| `200` | товар обновлён |
| `400` | тело не прошло проверку. Товар при этом не меняется |
| `404` | `Product {id} not found` |

### Удаление — `DELETE /products/{id}`

**Запрос:**
```http
DELETE /products/1
```

Удаляет строку из таблицы навсегда (hard delete). Товар, который есть хоть в одном заказе, удалить нельзя: старые заказы должны показывать, что в них купили.

**Ответ `204 No Content`** — без тела.

| Код | Когда |
|---|---|
| `204` | товар удалён |
| `404` | `Product {id} not found`, в том числе при повторном удалении |
| `409` | `Product {id} is used in orders and can't be deleted` |

## Заказы — `/orders`

Заказы текущего пользователя. Каждый запрос требует `Authorization: Bearer <access_token>`. Пользователь видит и меняет **только свои** заказы: чужой заказ для него не существует (`404`, а не `403`), так что по ответу нельзя узнать, есть ли заказ с таким `id`.

| Метод | Путь | Что делает | Успех |
|---|---|---|---|
| `POST` | `/orders` | оформить заказ | `201` |
| `GET` | `/orders` | мои заказы, новые сверху | `200` |
| `GET` | `/orders/{id}` | один мой заказ | `200` |
| `PATCH` | `/orders/{id}/status` | сменить статус | `200` |
| `GET` | `/orders/{id}/history` | история статусов, старые сверху | `200` |

Удаления нет: история заказов не должна пропадать. Вместо удаления заказ отменяют — статус `CANCELLED`.

Отдельных ручек для `order_items` и `order_status_history` тоже нет. Это части заказа: позиции приходят в теле `POST /orders` и возвращаются в поле `items`, а история пишется сама при каждой смене статуса.

### Список покупок и позиции заказа

Отдельной сущности «список покупок» (корзины) в базе нет. Клиент держит список у себя и присылает его целиком в теле `POST /orders`. Это DTO `CreateOrderRequest.items`: он живёт в памяти, пока обрабатывается запрос, и в базу не сохраняется. При оформлении заказа из каждой строки списка получается строка `order_items`:

```
CreateOrderRequest.items (тело запроса, не хранится)     order_items (таблица)
  { product_id: 1, quantity: 2 }          ──────────►      order_id, product_id = 1, quantity = 2, price = 79.90
                                          + цена берётся
                                            из products
```

То есть список покупок — это то, что присылает клиент, а `order_items` — его зафиксированная копия внутри заказа.

### Оформление — `POST /orders`

**Запрос:**
```http
POST /orders
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "items": [
    { "product_id": 1, "quantity": 2 },
    { "product_id": 7, "quantity": 1 }
  ]
}
```

| Поле | Правила |
|---|---|
| `items` | от 1 до 100 строк, один товар — одна строка |
| `product_id` | существующий товар |
| `quantity` | от 1 до 1000 |

**Как работает.** Всё происходит в одной транзакции: либо заказ оформлен целиком, либо ничего не изменилось.

```
POST /orders
   │
   ▼
products               блокируем строки товаров (SELECT ... FOR UPDATE),
   │                   проверяем остаток, уменьшаем quantity
   │
   ├──► orders                  1 строка: user_id, status = CREATED, created_at = момент покупки
   ├──► order_items             по строке на товар: product_id, quantity, price = текущая цена из products
   └──► order_status_history    1 строка: NULL → CREATED, changed_at, changed_by = пользователь
```

1. Проверяет тело. Если один товар указан дважды, возвращает `400`.
2. Блокирует строки нужных товаров в `products`. Пока транзакция не закончится, другой заказ с теми же товарами ждёт, поэтому два заказа не продадут последнюю пачку молока дважды. Строки блокируются в порядке `id`, чтобы два заказа не заблокировали друг друга навсегда (deadlock).
3. Для каждой строки проверяет остаток. Если хотя бы одного товара не хватает, возвращает `409`, и **ничего не списывается**, даже по товарам, которых хватало.
4. Уменьшает `products.quantity` на заказанное количество.
5. Создаёт заказ, копирует в `order_items` текущие цены товаров и пишет первую запись в историю.

**Ответ `201 Created`:**
```http
Location: http://localhost:8080/orders/1
```
```json
{
  "id": 1,
  "user_id": 5,
  "status": "CREATED",
  "items": [
    { "product_id": 1, "name": "Молоко 3,2%", "quantity": 2, "price": 79.90, "amount": 159.80 },
    { "product_id": 7, "name": "Хлеб Бородинский", "quantity": 1, "price": 59.00, "amount": 59.00 }
  ],
  "total": 218.80,
  "created_at": "2026-11-01T19:50:00Z",
  "completed_at": null
}
```

`price` — цена за штуку на момент заказа, `amount` = `price × quantity`, `total` — сумма всех `amount`.

| Код | Когда |
|---|---|
| `201` | заказ оформлен, товары списаны со склада |
| `400` | пустой список, `quantity` меньше 1, один товар указан дважды, `Product {id} not found` |
| `401` | нет токена или он недействителен |
| `409` | `Not enough stock for product {id}: requested N, available M` |

### Мои заказы — `GET /orders` и `GET /orders/{id}`

`GET /orders` возвращает массив заказов текущего пользователя, новые сверху. `GET /orders/{id}` возвращает один заказ. Формат заказа — как в ответе на `POST /orders`.

Позиции и товары загружаются тем же запросом, что и заказы (`@EntityGraph`), а не отдельным запросом на каждый заказ.

| Код | Когда |
|---|---|
| `200` | заказ или список |
| `401` | нет токена или он недействителен |
| `404` | `Order {id} not found`: заказа нет или он чужой |

### Смена статуса — `PATCH /orders/{id}/status`

**Запрос:**
```http
PATCH /orders/1/status
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "status": "PROCESSING"
}
```

Разрешённые переходы:

```
CREATED ──► PROCESSING ──► READY ──► COMPLETED
   │            │            │
   └────────────┴────────────┴──► CANCELLED
```

- Вперёд можно двигаться только на один шаг. Отменить заказ можно в любой момент до `COMPLETED`.
- `COMPLETED` и `CANCELLED` — конечные статусы, из них никуда нельзя.
- `completed_at` заполняется при переходе в `COMPLETED`.
- **Отмена возвращает товары на склад:** `products.quantity` увеличивается на количество из `order_items`. Вернуть их дважды нельзя, потому что `CANCELLED` — конечный статус.
- Каждая смена статуса добавляет запись в `order_status_history`.

**Ответ `200 OK`** — заказ с новым статусом.

| Код | Когда |
|---|---|
| `200` | статус изменён |
| `400` | неизвестный статус или нет поля `status` |
| `401` | нет токена или он недействителен |
| `404` | `Order {id} not found`: заказа нет или он чужой |
| `409` | `Can't change order status from X to Y`: переход не разрешён |

> Сейчас покупатель сам может перевести свой заказ в любой следующий статус. По смыслу `PROCESSING`, `READY` и `COMPLETED` ставят склад и курьер, а покупателю нужна только отмена. Это закроем, когда появится роль сотрудника.

### История статусов — `GET /orders/{id}/history`

**Ответ `200 OK`:**
```json
[
  { "from_status": null,         "to_status": "CREATED",    "changed_at": "2026-11-01T19:50:00Z", "changed_by": 5 },
  { "from_status": "CREATED",    "to_status": "PROCESSING", "changed_at": "2026-11-01T19:55:00Z", "changed_by": 5 },
  { "from_status": "PROCESSING", "to_status": "CANCELLED",  "changed_at": "2026-11-01T20:01:00Z", "changed_by": 5 }
]
```

| Код | Когда |
|---|---|
| `200` | история заказа |
| `401` | нет токена или он недействителен |
| `404` | `Order {id} not found`: заказа нет или он чужой |

## Известные ограничения

- **Товары без авторизации.** Создавать, менять и удалять товары может кто угодно. Нужна роль администратора.
- **Покупатель сам двигает статус заказа.** `PROCESSING`, `READY` и `COMPLETED` по смыслу ставят склад и курьер, покупателю нужна только отмена. Нужна роль сотрудника, сейчас есть только `CUSTOMER`.
- **Нет корзины.** Список покупок клиент держит у себя и присылает целиком в `POST /orders`.
- **Нет возвратов.** Выполненный заказ (`COMPLETED`) отменить нельзя, товар на склад не вернётся.
- **Отозванные токены живут в памяти** и пропадают при перезапуске. При нескольких экземплярах приложения это не работает, нужно общее хранилище, например Redis.
- **Пароль длиннее 72 байт** (например, длинный на кириллице) даёт `500`: BCrypt принимает максимум 72 байта, а проверка `@Size(max = 100)` считает символы.
- **В `ProductService` сейчас нет `@Transactional`.** Из-за этого `PUT /products/{id}` возвращает новые значения, но не сохраняет их в базу. Это ловят тест `ProductControllerTest.updateReplacesAllFields` и запрос 16 в `api.http`.

## Типичный сценарий

```
register / login  ──►  access_token + refresh_token
        │
        ├─ GET /users/me            (Authorization: Bearer access_token)
        │
        ├─ POST /orders             (список товаров в теле)  ──►  заказ, товары списаны со склада
        ├─ PATCH /orders/{id}/status                         ──►  CREATED → ... → COMPLETED или CANCELLED
        │
        ├─ access_token истёк  ──►  POST /auth/refresh  ──►  новая пара
        │
        └─ POST /auth/logout        (access в заголовке + refresh в теле)  ──►  оба токена отозваны
```
