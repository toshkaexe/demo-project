# lavka

Бэкенд онлайн-магазина продуктов на Java 21 и Spring Boot 4:

- **авторизация** по email и паролю на JWT-токенах;
- **каталог товаров** с остатками на складе;
- **заказы** с позициями по зафиксированной цене, списанием со склада и историей статусов.

Две роли: **покупатель** (`CUSTOMER`) и **сотрудник склада** (`WAREHOUSE`), см. [Роли](#роли).

Подтверждения почты, сессий, смены пароля, корзины и Redis пока нет: их сделаем в следующих итерациях.

## Запуск

### Что нужно

| Что | Зачем | Проверить |
|---|---|---|
| **Docker Desktop**, запущенный | Postgres всегда работает в контейнере; приложение тоже можно запустить в нём; тесты поднимают свой Postgres через Testcontainers | `docker compose version` |
| **JDK 21 или новее** | только для запуска без Docker (`./mvnw spring-boot:run`, IDE) и для тестов. Для запуска в Docker не нужен: образ собирается на своём JDK 21 | `java -version` |
| **Файл `.env`** с `JWT_SECRET` | ключ подписи токенов, не короче 32 байт. Файл не коммитится | `cat .env` |
| `jq` (необязательно) | только для скрипта демо-данных `src/test/fill_all.sh` | `jq --version` |

Maven ставить не нужно: в репозитории есть Maven wrapper (`./mvnw`), он сам скачает нужную версию.

**Один раз, перед первым запуском:**

```bash
cp .env.example .env
openssl rand -base64 48           # вывод вставить в .env: JWT_SECRET=...
```

### Вариант 1. Всё в Docker

Приложение и Postgres в контейнерах. Ничего, кроме Docker, не нужно.

```bash
docker compose up -d --build      # Postgres + приложение на http://localhost:8080
docker compose logs -f app        # логи приложения
docker compose down               # остановить (данные БД сохраняются)
```

- Образ собирается из `Dockerfile` в два этапа: JDK 21 + Maven wrapper собирают jar (без тестов), в итоговый образ попадают только JRE 21 и jar.
- **После изменений в коде** образ надо пересобрать: `docker compose up -d --build app`. Без `--build` запустится старая версия.
- Приложение в контейнере ходит в базу по адресу `postgres:5432` (переменные `SPRING_DATASOURCE_*` в `docker-compose.yaml`), `JWT_SECRET` берётся из `.env`. Без него `docker compose up` сразу падает с понятной ошибкой.
- Порт 8080 занят (например, приложение запущено ещё и из IDE): `APP_PORT=8090 docker compose up -d`.

### Вариант 2. База в Docker, приложение из IDE или Maven

Удобно для разработки: перезапуск быстрее, работает отладчик.

```bash
docker compose up -d postgres     # только Postgres на localhost:5432
./mvnw spring-boot:run            # приложение на http://localhost:8080
```

- Из IntelliJ: запустить `LavkaApplication` (`src/main/java/demo/lavka/LavkaApplication.java`). Рабочая папка — корень репозитория, иначе приложение не найдёт `.env`.
- Если контейнер `app` из варианта 1 тоже запущен, он уже занял 8080: остановите его (`docker compose stop app`) или запустите на другом порту.

### Проверить, что работает

```bash
curl http://localhost:8080/products     # 200 и список товаров ([] в пустой базе)
```

Swagger UI: http://localhost:8080/swagger-ui/index.html (подробнее ниже). Схему базы при старте создаёт Liquibase (`src/main/resources/db/changelog`), руками ничего создавать не нужно.

### Остановить и сбросить базу

```bash
docker compose down               # остановить, данные остаются в volume postgres-data
docker compose down -v            # остановить и удалить базу целиком
docker compose up -d --build      # при следующем старте Liquibase создаст схему заново
```

Данные переживают перезапуск контейнеров и компьютера. Удаляет их только `down -v`.

### Фронтенд

**Фронтенд** — то, что видит пользователь в браузере: страницы каталога, корзины, заказов, вход. Это **отдельное приложение в отдельном репозитории**, здесь его нет: этот репозиторий — только бэкенд, он отдаёт JSON по HTTP и ничего не рисует.

Локально фронтенд работает на **`http://localhost:3000`**: его dev-сервер (обычно Node.js: Vite, Next.js или Create React App) отдаёт браузеру страницы и JavaScript. Дальше JavaScript в браузере сам ходит за данными в этот бэкенд на `http://localhost:8080`:

```
браузер ──► http://localhost:3000   фронтенд: HTML, JS, CSS (отдельный репозиторий)
   │
   └──────► http://localhost:8080   этот бэкенд: JSON, /products, /orders, /auth/...
                     │
                     └──► Postgres на localhost:5432
```

Чтобы фронтенд работал, нужно запустить **оба** приложения: этот бэкенд (вариант 1 или 2) и фронтенд по инструкции из его репозитория. Без бэкенда страницы откроются, но данных в них не будет.

**Почему нужен CORS.** Для браузера `localhost:3000` и `localhost:8080` — разные сайты (разные порты). По умолчанию браузер не даёт JavaScript с одного сайта читать ответы другого. Бэкенд явно разрешает это фронтенду через CORS (`WebConfig.addCorsMappings`):

- разрешены адреса из `cors.allowed-origins` в `application-local.yaml`, сейчас `http://localhost:3000`. Несколько адресов — через запятую. `*` указывать нельзя, приложение не стартует;
- методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, заголовки `Authorization` и `Content-Type`; фронтенду открыт заголовок `Location`;
- cookie не используются: токен фронтенд передаёт в заголовке `Authorization: Bearer <access_token>`.

Если фронтенд запущен на другом порту (например, Vite по умолчанию использует `5173`), браузер покажет в консоли ошибку `blocked by CORS policy`. Добавьте этот адрес в `cors.allowed-origins` и перезапустите бэкенд.

Что фронтенд может вызывать и что получит в ответ, описано в спецификации `openapi.yaml` (Swagger UI ниже) и в разделе [Ручки](#ручки).

### Настройки

- **Профиль `local`.** Общие настройки лежат в `application.yaml`, локальные — в `application-local.yaml`: база `localhost:5432` (`lavka/lavka`), `JWT_SECRET` из `.env`, CORS для `http://localhost:3000`, текст ошибки в ответах, логи `demo.lavka` на уровне `debug`, Swagger UI и спецификация. Профиль включается по умолчанию, указывать `SPRING_PROFILES_ACTIVE` не нужно.
- **Тесты** (`./mvnw test`) поднимают свой Postgres через Testcontainers, поэтому нужен запущенный Docker. Локальная база тестами не затрагивается. Подробнее — в разделе [Тесты](#тесты).
- **Lombok.** В IntelliJ нужен плагин Lombok (в новых версиях встроен) и включённая галочка *Settings → Build → Compiler → Annotation Processors → Enable annotation processing*. После изменения `pom.xml` — *Reload Maven Project*. Версия Lombok закреплена в `pom.xml` (`1.18.48`): версия 1.18.46, которую подтягивает Spring Boot, роняет компилятор на JDK 27 (`ExceptionInInitializerError: EndPosTable`).

**Swagger UI** — http://localhost:8080/swagger-ui/index.html. Он показывает спецификацию `src/main/resources/openapi/openapi.yaml` (OpenAPI 3.1, написана вручную: описания, все коды ошибок, примеры), она отдаётся по адресу `/openapi.yaml`. Чтобы отправить запрос к закрытой ручке, нажмите **Authorize** и вставьте `access_token` без слова `Bearer`. Спецификация, сгенерированная из кода (springdoc), лежит на `/v3/api-docs`. Если меняете ручки, обновляйте и `openapi.yaml`.

**Спецификация открыта только в профиле `local`.** В ней перечислены все ручки, роли и коды ошибок: на машине разработчика это удобно, а снаружи — готовая разведка для атакующего. Поэтому в `application.yaml` springdoc выключен (`springdoc.api-docs.enabled` и `springdoc.swagger-ui.enabled` — `false`), а включает его `application-local.yaml`. Без профиля `local` (тесты, будущий прод) `/swagger-ui/index.html`, `/v3/api-docs` и `/openapi.yaml` отвечают `404`.

- `openapi.yaml` лежит в `resources/openapi/`, а не в `static/`: всё из `static/` Spring отдаёт всем и всегда, в любом профиле. Файл отдаёт `OpenApiDocsConfig`, и только пока включён Swagger UI.
- Пока профиль `local` включён по умолчанию (см. [Известные ограничения](#известные-ограничения)), спецификация открыта и в Docker. Перед выкладкой в прод это закроется вместе с отказом от профиля по умолчанию.
- Проверяет `OpenApiDocsTest`.

**Демо-данные** во все таблицы: `./src/test/fill_all.sh` (нужны запущенное приложение, `jq` и контейнер `lavka-postgres`). Скрипт работает через API, поэтому данные согласованы так же, как при настоящих запросах: заводит сотрудника склада `warehouse@lavka.local` (роль выдаёт через `UPDATE` в базе), от его имени создаёт 20 товаров, затем 5 покупателей `customer1…5@gmail.com` (у всех пароль `123456`), каждому два адреса доставки (дом — активный, и работа) и по 4 заказа, которые доходят до статусов `COMPLETED`, `READY`, `CANCELLED` и `CREATED`. Товары с остатком списываются, у отменённых возвращаются, история пишется на каждый шаг. Повторный запуск не дублирует товары и пользователей, но добавляет новые заказы. Другой адрес: `BASE_URL=http://localhost:8090 ./src/test/fill_all.sh`.

Сценарий для IntelliJ HTTP Client лежит в `src/test/api.http`: 50 с лишним запросов ко всем ручкам, каждый проверяет свой ответ. Выберите окружение `dev` (`src/test/http-client.env.json`) и нажмите **Run All Requests in File**. Запросы передают друг другу токены и `id`, email каждый раз новый, поэтому файл можно запускать сколько угодно раз. Каждый запуск оставляет в локальной базе тестового пользователя, два товара и отменённый заказ.

## Как устроен код

```
demo.lavka
├── controller   HTTP: принимает запрос, проверяет тело (@Valid), выбирает код ответа
├── service      бизнес-логика и транзакции: проверки, 404/409, склад, логирование
├── repository   Spring Data JPA: запросы к базе
├── entity       JPA-сущности, один к одному с таблицами
├── model        DTO: тела запросов и ответов
├── auth         JWT, пароли, проверка токенов и ролей (@RequireRole, @Authenticated, @CurrentUser + RoleInterceptor)
└── config       настройки: ключ JWT, BCrypt, CORS для фронтенда (CorsConfig), спецификация только при включённом Swagger UI (OpenApiDocsConfig), регистрация RoleInterceptor, CurrentUserArgumentResolver и CORS (WebConfig)
```

Запрос проходит слои по порядку: `Controller → Service → Repository → база`.

- **Наружу отдаются только DTO** (`ProductResponse`, `OrderResponse`, `UserResponse` и т. д.), а не JPA-сущности. Страница списка — общий `PageResponse<T>` (`content`, `page`, `size`, `total_elements`, `total_pages`), сейчас его отдаёт только `GET /orders`. Так в ответ не попадёт лишнее, например хеш пароля, и не сработает случайно ленивая загрузка связей.
- **Транзакции на сервисе.** В `application.yaml` стоит `spring.jpa.open-in-view: false`, поэтому сессия Hibernate живёт только внутри `@Transactional`-метода сервиса. Это важно в двух случаях:
  - метод меняет сущность и не вызывает `save()`. Изменения записывает dirty checking при коммите, а он работает, только пока сущность **managed** (прикреплена к открытой сессии). Без транзакции сущность сразу становится **detached**, и изменения молча теряются;
  - метод обращается к ленивым (`LAZY`) связям. Вне транзакции это `LazyInitializationException`.

  Чтение помечено `@Transactional(readOnly = true)`: Hibernate не хранит снимки сущностей и не проверяет их на изменения.
- **Проверка данных в трёх местах:** Bean Validation на DTO в контроллере (клиент получает понятный `400`), проверки в сервисе (страховка для вызовов не из контроллера: тоже `400` с причиной, а не `NullPointerException` или `IllegalArgumentException`, которые клиент увидел бы как `500`) и `CHECK`, `NOT NULL`, внешние ключи в базе (последняя линия защиты).
- **Схема только через Liquibase.** Hibernate работает в режиме `ddl-auto: validate`: он сверяет сущности с таблицами и не даёт приложению стартовать, если они разошлись. Применённые changeset'ы не меняют, для изменений пишут новый файл в `db/changelog/changes`.
- **Lombok на сущностях** — только `@Getter`, `@Setter` на изменяемых полях, `@Builder` и `@NoArgsConstructor(access = PROTECTED)` для JPA. `@Data`, `@EqualsAndHashCode` и `@ToString` на сущностях не используем: они обращаются ко всем полям, включая ленивые связи. Это `LazyInitializationException`, лишние запросы или бесконечная рекурсия в `toString` при двусторонних связях, а `hashCode` меняется после `persist`, когда появляется `id`.
- **Позиции и история — часть заказа.** `OrderItem` и `OrderStatusHistory` создаются только через методы `Orders` (`addItem`, `changeStatus`) и сохраняются вместе с заказом через `cascade`. Поэтому сменить статус мимо истории нельзя.

## Роли

| Роль | Кто | Как получить | Что может |
|---|---|---|---|
| `CUSTOMER` | покупатель | выдаётся при регистрации | смотреть каталог; оформлять заказы; видеть **свои** заказы и их историю; **отменять** свои заказы |
| `WAREHOUSE` | сотрудник склада | только в базе, через API нельзя | всё, что покупатель, плюс: создавать, менять и удалять товары; видеть **все** заказы; проводить заказы по статусам `PROCESSING → READY → COMPLETED` |

**Где хранится роль.** В колонке `users.role`, а не в токене. В токене лежит только id пользователя (`sub`). На каждый запрос `AuthService.authenticate` загружает пользователя из базы вместе с ролью. Поэтому смена роли или удаление пользователя действует сразу, без перевыпуска токенов. Цена — один `SELECT` по первичному ключу на запрос.

**Как назначить сотрудника склада.** Зарегистрировать пользователя обычным `POST /auth/register`, затем:

```sql
UPDATE users SET role = 'WAREHOUSE' WHERE email = 'warehouse@lavka.local';
```

Перелогиниваться не нужно: уже выданный токен сразу работает с новой ролью. Ручки для смены роли нет намеренно, иначе любой мог бы сделать себя сотрудником. База принимает только известные роли (`CHECK` из миграции `005`).

**Как проверяется доступ.**
- **Товары.** Методы записи помечены `@RequireRole(Role.WAREHOUSE)`. Аннотацию проверяет `RoleInterceptor`, который регистрируется в `WebConfig`. Он срабатывает после выбора метода контроллера, но **до чтения тела запроса**. Поэтому клиент без прав получает `401`/`403`, а не ошибки валидации, по которым можно изучить API.
- **Заказы, адреса, `/users/me`.** Нужен любой валидный токен: контроллеры `OrderController` и `AddressController` целиком и метод `/users/me` помечены `@Authenticated`. Её проверяет тот же `RoleInterceptor`, тоже до тела, поэтому `POST /orders` или `PUT /users/me/addresses/{id}` без токена с битым телом дают `401`, а не `400`. Найденного пользователя interceptor кладёт в запрос, а метод получает его параметром `@CurrentUser User user`. Сами контроллеры токен не читают. Если поставить `@CurrentUser` на ручку без `@Authenticated` или `@RequireRole`, запрос упадёт с `IllegalStateException`: это ошибка в коде, а не тихий `null`.
- **Заказы.** Права зависят от того, чей заказ и какой статус ставят, поэтому проверка живёт в `OrderService`:
  - покупатель ищет заказы только среди своих (чужой даёт `404`);
  - на смену статуса, кроме `CANCELLED`, покупатель получает `403`.
- **Текст `403` всегда нейтральный:** `Access denied`. Имена ролей и то, какая роль нужна, в ответ не попадают, чтобы по ответам нельзя было изучить устройство прав. Подробности (`userId`, его роль, какая нужна, что пытался сделать) пишутся в лог с уровнем `WARN`.

| Ситуация | Код |
|---|---|
| нет токена, токен истёк или подделан | `401` |
| токен есть, но роль не подходит | `403` |

## Как устроены токены

После регистрации и логина клиент получает пару токенов:

```json
{
  "access_token":  "eyJhbGciOiJIUzUxMiJ9...",
  "refresh_token": "eyJhbGciOiJIUzUxMiJ9..."
}
```

| | access_token | refresh_token |
|---|---|---|
| Для чего | передаётся с каждым запросом в `Authorization: Bearer <token>` | только чтобы получить новую пару в `POST /auth/refresh` |
| Срок жизни | 15 минут (`auth.jwt.access-ttl`) | 30 дней (`auth.jwt.refresh-ttl`) |
| Внутри | `sub` = id пользователя, `typ` = `access` | `sub` = id пользователя, `typ` = `refresh` |

- Оба токена — JWT, подписанные ключом из `.env`. Подделать их нельзя, но прочитать содержимое может кто угодно. Поэтому в токен не кладём ничего секретного.
- Поле `typ` не даёт использовать refresh-токен вместо access-токена и наоборот.
- Все проверки токена собраны в одном методе `JWTService.validateToken(token, expectedType)`. Он проверяет по порядку:
  1. **подпись**: jjwt пересчитывает HMAC от `header.payload` нашим ключом и сравнивает с подписью токена;
  2. **срок**: `exp` не в прошлом;
  3. **тип**: `typ` совпадает с ожидаемым (`access` или `refresh`);
  4. **отзыв**: токен не отозван через logout или refresh.

  На первой же неудаче метод бросает `InvalidTokenException` с причиной (`BAD_SIGNATURE`, `EXPIRED`, `WRONG_TYPE`, `REVOKED`, `MALFORMED`), и клиент получает `401`.
- Отозванные токены (после выхода или обмена refresh-токена) хранятся в памяти приложения до окончания своего срока. **После перезапуска приложения этот список очищается.**

## Таблица `users`

| Колонка | Тип | |
|---|---|---|
| `id` | `BIGSERIAL` | первичный ключ |
| `email` | `VARCHAR(254)` | уникальный, хранится в нижнем регистре |
| `password_hash` | `VARCHAR(100)` | BCrypt-хеш, сам пароль нигде не хранится |

## Как связаны таблицы

```
users ──< orders ──< order_items >── products
  │           │
  │           └──< order_status_history
  │
  └──< user_addresses        (в orders копируется, ссылки нет)
```

- `user_addresses.active` — адрес, на который по умолчанию оформляется заказ. В момент оформления он копируется в колонки `orders.delivery_*`.

- `products.price` — **текущая** цена товара, её можно менять.
- `order_items.price` — копия цены **на момент заказа**, а сам момент заказа — `orders.created_at`.
- По `order_items.product_id` находится товар в `products`, оттуда берётся, например, его название.
- `products.quantity` — остаток на складе. Заказ уменьшает его, отмена заказа возвращает обратно. Подробнее — в разделе [Остатки и блокировки](#остатки-и-блокировки).

## Остатки и блокировки

**Когда меняется `products.quantity`:**

| Действие | Остаток |
|---|---|
| `POST /orders` — оформление | уменьшается на заказанное сразу. Если хотя бы одного товара не хватает, `409`, и не списывается ничего |
| `CREATED → CANCELLED` — отмена | заказанное возвращается |
| `PROCESSING`, `READY`, `COMPLETED` | не меняется: товар списан ещё при оформлении |
| `PUT /products/{id}` — правка склада | задаётся числом из запроса |

Отрицательный остаток запрещает `CHECK (quantity >= 0)` в базе: это последняя страховка, если проверка в коде не сработала.

**Где стоят пессимистические блокировки** (`SELECT ... FOR UPDATE`, строка заблокирована до коммита транзакции):

| Операция | Что блокирует | От чего защищает |
|---|---|---|
| Оформление заказа (`OrderService.create`) | строки всех товаров заказа, по возрастанию `id` | два заказа не продадут последнюю единицу дважды |
| Смена статуса (`OrderService.changeStatus`) | строку заказа (покупатель — только своего: владелец проверяется в том же `SELECT ... FOR UPDATE`), при отмене затем строки его товаров | две одновременные отмены не вернут товар дважды, отмена и взятие в сборку не пройдут оба |
| Правка товара (`ProductService.update`) | строку товара | правка и заказ с этим товаром не перемешиваются: правка ждёт идущий заказ и видит новый остаток, заказ ждёт правку |
| Добавление, удаление адреса и смена активного (`AddressService.create`, `delete`, `activate`) | строку пользователя в `users` | параллельные запросы одного пользователя не обойдут лимит в 10 адресов и не оставят два активных или ни одного |

**Дедлоков нет**, потому что блокировки всегда берутся в одном порядке: сначала заказ, потом товары по возрастанию `id`. Оформление заказа берёт только товары, правка — только один товар. Адреса блокируют только строку пользователя, а её не блокирует больше никто. Оформление заказа читает адрес без блокировки: оно копирует его в заказ, поэтому удаление адреса в ту же секунду уже не важно.

**Чего блокировка не решает.** Она держится только время одного запроса, миллисекунды. Число, которое сотрудник склада отправляет в `PUT`, он видел раньше, в другом запросе:

```
GET  /products/1              → склад видит quantity 10
POST /orders (3 шт)           → 7, заказ закоммичен, блокировка снята
PUT  /products/1 {quantity: 15}  → «привезли 5» посчитано от старых 10, записывается 15
```

Продажа 3 штук теряется. От этого защищают оптимистическая блокировка (версия товара в `PUT`, при устаревшей — `409`) или отдельная операция «приход +N / списание −N» вместо абсолютного `quantity`. Пока не сделано, см. [Известные ограничения](#известные-ограничения).

## Ручки

### Регистрация — `POST /auth/register`

Создаёт пользователя и сразу выдаёт пару токенов, так что отдельно логиниться не нужно.

**Запрос:**
```http
POST /auth/register
Content-Type: application/json

{
  "email": "anton@example.com",
  "password": "123456"
}
```

**Как работает:**
1. Проверяет тело: `email` должен быть корректным адресом длиной до 254 символов, `password` — от 6 до 100 символов.
2. Приводит email к нижнему регистру и обрезает пробелы, поэтому `Anton@Example.com` и `anton@example.com` — один и тот же пользователь.
3. Если такой email уже есть, возвращает `409`.
4. Хеширует пароль через BCrypt и сохраняет пользователя в `users`.
5. Выдаёт пару токенов.

**Ответ `201 Created`:**
```json
{ "access_token": "...", "refresh_token": "..." }
```

| Код | Когда |
|---|---|
| `201` | пользователь создан |
| `400` | неверный email, пароль короче 6 символов или не хватает полей |
| `409` | `User already exists`: такой email уже зарегистрирован |

### Логин — `POST /auth/login`

Вход только по email и паролю.

**Запрос:**
```http
POST /auth/login
Content-Type: application/json

{
  "email": "anton@example.com",
  "password": "123456"
}
```

**Как работает:**
1. Находит пользователя по email без учёта регистра.
2. Сверяет пароль с хешем из базы через `BCrypt.matches`. Если такого email нет, пароль всё равно сверяется, но с фиктивным хешем, созданным при старте. Иначе ответ для несуществующего email приходил бы на десятки миллисекунд быстрее, и по времени можно было бы перебором узнать, какие email зарегистрированы.
3. В лог пишется только `userId`, email не пишется никогда. Это персональные данные, а `email` в логине не проверяется на формат: перевод строки в нём подделал бы строки лога. У неизвестного email в логе только `Login failed: unknown email`.
4. Выдаёт новую пару токенов. Каждый логин даёт отдельную пару, поэтому можно войти с нескольких устройств одновременно.

**Ответ `200 OK`:**
```json
{ "access_token": "...", "refresh_token": "..." }
```

| Код | Когда |
|---|---|
| `200` | вход выполнен |
| `400` | пустой email или пароль |
| `401` | `Invalid email or password`: такого email нет или пароль неверный. Ответ одинаковый в обоих случаях, чтобы по нему нельзя было узнать, зарегистрирован ли email |

### Выход — `POST /auth/logout`

Отзывает оба токена пары: и access, и refresh.

**Запрос:**
```http
POST /auth/logout
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "refresh_token": "<refresh_token>"
}
```

**Как работает:**
1. Проверяет refresh-токен из тела: подпись, срок действия, `typ = refresh`, токен не отозван.
2. Проверяет access-токен из заголовка так же, но **истёкший срок допускается**: access живёт 15 минут, и выйти нужно уметь и позже. Он должен принадлежать **тому же** пользователю.
3. Добавляет оба токена в список отозванных, сначала refresh.

Остальные логины этого пользователя, например на другом устройстве, продолжают работать.

**Ответ `204 No Content`** — без тела.

| Код | Когда |
|---|---|
| `204` | выход выполнен |
| `400` | в теле нет `refresh_token` |
| `401` | `Missing bearer token`: нет заголовка. `Token expired`: истёк refresh-токен (истёкший access не мешает). `Invalid token`: токен подделан, отозван или не того типа. `Refresh token belongs to another user`: refresh-токен другого пользователя |

### Текущий пользователь — `GET /users/me`

Возвращает данные пользователя, которому принадлежит access-токен. Тело запроса не нужно.

**Запрос:**
```http
GET /users/me
Authorization: Bearer <access_token>
```

**Как работает:**
1. Берёт токен из заголовка `Authorization: Bearer ...`.
2. Проверяет, что это действующий и не отозванный access-токен.
3. Достаёт из токена id пользователя (`sub`) и загружает пользователя из базы.

**Ответ `200 OK`:**
```json
{
  "id": 1,
  "email": "anton@example.com",
  "role": "CUSTOMER",
  "created_at": "2026-10-20T18:02:52.773189Z",
  "updated_at": "2026-10-20T18:02:52.773189Z"
}
```

Хеш пароля в ответ не попадает.

| Код | Когда |
|---|---|
| `200` | данные пользователя |
| `401` | `Missing bearer token`: нет заголовка. `Token expired`: access-токен истёк, пора вызвать `/auth/refresh`. `Invalid token`: токен подделан, отозван или передан refresh вместо access. `User not found`: пользователь удалён |

### Адреса доставки — `/users/me/addresses`

Адреса текущего пользователя (таблица `user_addresses`). У пользователя может быть несколько адресов: дом, работа, дача. Нужен access-токен; роль не важна, но каждый работает только **со своими** адресами. Чужой адрес отвечает `404`, как будто его нет.

| Метод | Путь | Что делает | Ответ |
|---|---|---|---|
| `GET` | `/users/me/addresses` | все свои адреса в порядке добавления | `200`, массив (пустой, если адресов нет) |
| `GET` | `/users/me/addresses/{id}` | один адрес | `200` |
| `POST` | `/users/me/addresses` | добавить адрес | `201`, заголовок `Location: /users/me/addresses/{id}` |
| `PUT` | `/users/me/addresses/{id}` | заменить все поля адреса | `200` |
| `PUT` | `/users/me/addresses/{id}/active` | сделать адрес активным, тело не нужно | `200` |
| `DELETE` | `/users/me/addresses/{id}` | удалить адрес | `204` |

**Тело `POST` и `PUT`:**
```json
{
  "postal_code": "101000",
  "country": "Россия",
  "city": "Москва",
  "street": "Тверская",
  "house": "12к2",
  "apartment": "45",
  "recipient_name": "Антон Иванов",
  "courier_note": "подъезд 3, домофон 45"
}
```

| Поле | Обязательное | Макс. длина | Примечание |
|---|---|---|---|
| `postal_code` | да | 20 | формат не проверяется: в разных странах он разный |
| `country`, `city` | да | 100 | |
| `street` | да | 300 | |
| `house` | да | 20 | строка: `12к2`, `5А`, `10 стр. 3` |
| `apartment` | нет | 20 | `null` или пусто для частного дома |
| `recipient_name` | да | 200 | имя и фамилия получателя |
| `courier_note` | нет | 500 | подъезд, этаж, код домофона |

Пробелы по краям обрезаются. Пустые `apartment` и `courier_note` сохраняются как `null`. Ответ — тот же адрес с `id`, `active`, `created_at` и `updated_at`.

**Активный адрес** — тот, куда везут заказы. В таблице это колонка `active`, а частичный уникальный индекс `user_addresses_one_active_idx` (`(user_id) WHERE active`) не даёт базе сохранить два активных адреса одного пользователя.

- Первый адрес становится активным сам, следующие добавляются неактивными.
- `PUT /users/me/addresses/{id}/active` делает адрес активным, а прежний активный выключает. Сначала в базу записывается выключение старого, потом включение нового, иначе индекс отклонит запрос. Повторный вызов ничего не меняет.
- `PUT /users/me/addresses/{id}` меняет поля адреса, но не признак `active`.
- Если удалить активный адрес, активным становится самый старый из оставшихся. Так у пользователя с адресами всегда ровно один активный.
- Добавление, удаление и смена активного адреса блокируют строку пользователя (`SELECT ... FOR UPDATE`). Параллельные запросы одного пользователя выполняются по очереди, поэтому не могут вместе обойти лимит или оставить два активных адреса.

| Код | Когда |
|---|---|
| `400` | обязательное поле пустое или значение длиннее лимита |
| `401` | нет токена или он недействителен, как у `/users/me`. Проверяется раньше тела: без токена `401`, даже если тело битое |
| `404` | `Address {id} not found`: адреса нет или он чужой |
| `409` | `Address limit reached`: у пользователя уже 10 адресов |

### Обновление пары — `POST /auth/refresh`

Когда access-токен истёк, клиент меняет refresh-токен на новую пару без повторного ввода пароля.

```http
POST /auth/refresh
Content-Type: application/json

{
  "refresh_token": "<refresh_token>"
}
```

- Возвращает `200` и новую пару `{ "access_token", "refresh_token" }`.
- Старый refresh-токен сразу отзывается: каждый refresh-токен можно использовать только один раз.
- Возвращает `401`: `Token expired`, если refresh-токен истёк (нужен новый логин), или `Invalid token`, если он подделан, уже использован или вместо refresh передан access-токен.

## Товары — `/products`

Каталог товаров: просмотр, создание, изменение и удаление строк таблицы `products`.

> **Читать каталог может кто угодно**, без токена. **Создавать, менять и удалять товары может только сотрудник склада** (`WAREHOUSE`): нужен заголовок `Authorization: Bearer <access_token>`. Без токена ответ `401`, с токеном покупателя — `403 Access denied`.

| Метод | Путь | Что делает | Успех |
|---|---|---|---|
| `GET` | `/products` | список всех товаров | `200` |
| `GET` | `/products/{id}` | один товар | `200` |
| `POST` | `/products` | создать товар | `201` |
| `PUT` | `/products/{id}` | заменить все поля товара | `200` |
| `DELETE` | `/products/{id}` | удалить товар | `204` |

Как запрос проходит через приложение:

```
ProductController  ──►  ProductService  ──►  ProductRepository  ──►  таблица products
  проверка тела           бизнес-проверки,       Spring Data JPA
  (@Valid), коды          транзакция, 404,
  ответов, Location       логирование
```

- Наружу всегда отдаётся `ProductResponse`, а не сама JPA-сущность `Products`.
- Правила для полей проверяются в трёх местах: тело запроса (Bean Validation в контроллере, ответ `400`), `ProductService.validate(...)` и `CHECK`-ограничения в базе. Последние два — страховка на случай, если товар создаёт не контроллер, а другой код. `validate` проверяет то же, что Bean Validation, включая длину названия (255) и цифры цены (8 до точки, 2 после), до любого `trim()`, и отвечает `400`, а не ошибкой базы.

### Тело товара

Одинаковое для создания и изменения:

```json
{
  "name": "Молоко 3,2%",
  "quantity": 10,
  "price": 89.90
}
```

| Поле | Правила |
|---|---|
| `name` | обязательное, не пустое и не из одних пробелов. Пробелы по краям обрезаются |
| `quantity` | обязательное, целое, `>= 0` |
| `price` | обязательное, `>= 0`, не больше двух знаков после запятой и не больше `99 999 999.99` (колонка `NUMERIC(10, 2)`) |

Цена хранится в `BigDecimal`, а не в `double`, поэтому копейки не теряются на округлении.

[
  { "id": 1, "name": "Молоко 3,2%", "quantity": 10, "price": 89.90 },
  { "id": 2, "name": "Хлеб",        "quantity": 5,  "price": 45.00 }

### Создание — `POST /products`

**Запрос:**
```http
POST /products
Authorization: Bearer <access_token сотрудника склада>
Content-Type: application/json

{
  "name": "Молоко 3,2%",
  "quantity": 10,
  "price": 89.90
}
```

**Как работает:**
1. Контроллер проверяет тело по правилам из таблицы выше. При ошибке возвращает `400`, до базы запрос не доходит.
2. Сервис обрезает пробелы в `name` и ещё раз проверяет значения.
3. Собирает сущность через `Products.builder()` и сохраняет её. `id` выдаёт база.
4. Возвращает созданный товар и его адрес в заголовке `Location`.

**Ответ `201 Created`:**
```http
Location: http://localhost:8080/products/1
```
```json
{ "id": 1, "name": "Молоко 3,2%", "quantity": 10, "price": 89.90 }
```

| Код | Когда |
|---|---|
| `201` | товар создан |
| `400` | не хватает поля, пустое `name`, отрицательные `quantity` или `price`, больше двух знаков в `price` |
| `401` | нет токена или он недействителен |
| `403` | `Access denied`: токен покупателя |

### Изменение — `PUT /products/{id}`

Заменяет **все** поля товара сразу, поэтому в теле нужны все три поля, как при создании. Частичного обновления (`PATCH`) пока нет.

**Запрос:**
```http
PUT /products/1
Authorization: Bearer <access_token сотрудника склада>
Content-Type: application/json

{
  "name": "Молоко 2,5%",
  "quantity": 7,
  "price": 79.90
}
```

**Как работает:**
1. Проверяет тело так же, как при создании.
2. Загружает товар по `id` с пессимистической блокировкой (`SELECT ... FOR UPDATE`). Если его нет, возвращает `404`. Строка остаётся заблокированной до коммита: если сейчас идёт оформление или отмена заказа с этим товаром, правка ждёт её завершения и видит уже новый остаток, а заказы, пришедшие во время правки, ждут её. Изменения одного товара никогда не перемешиваются. Дедлока нет: правка блокирует одну строку товара, заказы блокируют товары по возрастанию `id`.
3. Меняет поля через сеттеры. Отдельный `save()` не вызывается: метод работает в транзакции (`@Transactional`), и при коммите Hibernate сам замечает изменённые поля и делает `UPDATE` (dirty checking).
4. Возвращает обновлённый товар.

**Ответ `200 OK`:**
```json
{ "id": 1, "name": "Молоко 2,5%", "quantity": 7, "price": 79.90 }
```

| Код | Когда |
|---|---|
| `200` | товар обновлён |
| `400` | тело не прошло проверку. Товар при этом не меняется |
| `401` | нет токена или он недействителен |
| `403` | `Access denied`: токен покупателя |
| `404` | `Product {id} not found` |

### Удаление — `DELETE /products/{id}`

**Запрос:**
```http
DELETE /products/1
Authorization: Bearer <access_token сотрудника склада>
```

Удаляет строку из таблицы навсегда (hard delete). Товар, который есть хоть в одном заказе, удалить нельзя: старые заказы должны показывать, что в них купили.

**Ответ `204 No Content`** — без тела.

| Код | Когда |
|---|---|
| `204` | товар удалён |
| `401` | нет токена или он недействителен |
| `403` | `Access denied`: токен покупателя |
| `404` | `Product {id} not found`, в том числе при повторном удалении |
| `409` | `Product {id} is used in orders and can't be deleted` |

## Заказы — `/orders`

Каждый запрос требует `Authorization: Bearer <access_token>`. Что видно и что можно, зависит от [роли](#роли):

- **покупатель** оформляет заказы, видит **только свои** и может их **только отменить**. Чужой заказ для него не существует (`404`, а не `403`), так что по ответу нельзя узнать, есть ли заказ с таким `id`;
- **сотрудник склада** видит **все** заказы и проводит их по статусам: собирает (`PROCESSING`), отмечает собранным (`READY`) и выполненным (`COMPLETED`). Может и отменить заказ.

| Метод | Путь | Что делает | Успех |
|---|---|---|---|
| `POST` | `/orders` | оформить заказ | `201` |
| `GET` | `/orders` | мои заказы, новые сверху | `200` |
| `GET` | `/orders/{id}` | один мой заказ | `200` |
| `PATCH` | `/orders/{id}/status` | сменить статус | `200` |
| `GET` | `/orders/{id}/history` | история статусов, старые сверху | `200` |

Удаления нет: история заказов не должна пропадать. Вместо удаления заказ отменяют — статус `CANCELLED`.

Отдельных ручек для `order_items` и `order_status_history` тоже нет. Это части заказа: позиции приходят в теле `POST /orders` и возвращаются в поле `items`, а история пишется сама при каждой смене статуса.

### Список покупок и позиции заказа

Отдельной сущности «список покупок» (корзины) в базе нет. Клиент держит список у себя и присылает его целиком в теле `POST /orders`. Это DTO `CreateOrderRequest.items`: он живёт в памяти, пока обрабатывается запрос, и в базу не сохраняется. При оформлении заказа из каждой строки списка получается строка `order_items`:

```
CreateOrderRequest.items (тело запроса, не хранится)     order_items (таблица)
  { product_id: 1, quantity: 2 }          ──────────►      order_id, product_id = 1, quantity = 2, price = 79.90
                                          + цена берётся
                                            из products
```

То есть список покупок — это то, что присылает клиент, а `order_items` — его зафиксированная копия внутри заказа.

### Оформление — `POST /orders`

**Запрос:**
```http
POST /orders
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "items": [
    { "product_id": 1, "quantity": 2 },
    { "product_id": 7, "quantity": 1 }
  ],
  "address_id": 3
}
```

| Поле | Правила |
|---|---|
| `items` | от 1 до 100 строк, один товар — одна строка |
| `product_id` | существующий товар |
| `quantity` | от 1 до 1000 |
| `address_id` | необязательное: один из **своих** адресов доставки. Не указан — заказ едет на активный адрес |

**Адрес доставки.** Без адреса заказ не оформить: сначала нужно добавить его через `POST /users/me/addresses`. В заказ копируется сам адрес, колонки `delivery_*` в `orders`, а не ссылка на него. Поэтому если потом поменять или удалить адрес в профиле, старые заказы всё равно поедут туда, куда их оформили. У заказов, оформленных до появления адресов, эти колонки пустые; `CHECK` не даёт сохранить адрес наполовину.

**Как работает.** Всё происходит в одной транзакции: либо заказ оформлен целиком, либо ничего не изменилось.

```
POST /orders
   │
   ▼
products               блокируем строки товаров (SELECT ... FOR UPDATE),
   │                   проверяем остаток, уменьшаем quantity
   │
   ├──► orders                  1 строка: user_id, status = CREATED, created_at = момент покупки
   ├──► order_items             по строке на товар: product_id, quantity, price = текущая цена из products
   └──► order_status_history    1 строка: NULL → CREATED, changed_at, changed_by = пользователь
```

1. Проверяет тело. Если один товар указан дважды, возвращает `400`. Находит адрес доставки: указанный или активный. Если адреса нет или он чужой — `400`.
2. Блокирует строки нужных товаров в `products`. Пока транзакция не закончится, другой заказ с теми же товарами ждёт, поэтому два заказа не продадут последнюю пачку молока дважды. Строки блокируются в порядке `id`, чтобы два заказа не заблокировали друг друга навсегда (deadlock).
3. Для каждой строки проверяет остаток. Если хотя бы одного товара не хватает, возвращает `409`, и **ничего не списывается**, даже по товарам, которых хватало.
4. Уменьшает `products.quantity` на заказанное количество.
5. Создаёт заказ, копирует в `order_items` текущие цены товаров и пишет первую запись в историю.

**Ответ `201 Created`:**
```http
Location: http://localhost:8080/orders/1
```
```json
{
  "id": 1,
  "user_id": 5,
  "status": "CREATED",
  "items": [
    { "product_id": 1, "name": "Молоко 3,2%", "quantity": 2, "price": 79.90, "amount": 159.80 },
    { "product_id": 7, "name": "Хлеб Бородинский", "quantity": 1, "price": 59.00, "amount": 59.00 }
  ],
  "total": 218.80,
  "created_at": "2026-11-01T19:50:00Z",
  "completed_at": null,
  "delivery_address": {
    "recipient_name": "Антон Иванов",
    "postal_code": "101000",
    "country": "Россия",
    "city": "Москва",
    "street": "Тверская",
    "house": "12к2",
    "apartment": "45",
    "courier_note": "подъезд 3, домофон 45"
  }
}
```

`price` — цена за штуку на момент заказа, `amount` = `price × quantity`, `total` — сумма всех `amount`.

| Код | Когда |
|---|---|
| `201` | заказ оформлен, товары списаны со склада |
| `400` | пустой список или больше 100 строк, `quantity` меньше 1 или больше 1000, нет `product_id`, битый JSON, один товар указан дважды, `Product {id} not found`, `Address {id} not found` (адреса нет или он чужой), `No delivery address` (у пользователя нет адресов) |
| `401` | нет токена или он недействителен. Проверяется раньше тела: без токена `401`, даже если тело битое |
| `409` | `Not enough stock for product {id}: requested N, available M` |

### Список и один заказ — `GET /orders` и `GET /orders/{id}`

`GET /orders` возвращает заказы **страницами**, новые сверху: покупателю — его заказы, сотруднику склада — все. `GET /orders/{id}` возвращает один заказ. Формат заказа — как в ответе на `POST /orders`.

```http
GET /orders?page=0&size=20
Authorization: Bearer <access_token>
```

| Параметр | По умолчанию | Правила |
|---|---|---|
| `page` | `0` | номер страницы, с 0 |
| `size` | `20` | от 1 до **100** (`OrderService.MAX_PAGE_SIZE`) |

**Ответ:**
```json
{
  "content": [ { "id": 42, "status": "CREATED", "items": [ ... ], ... } ],
  "page": 0,
  "size": 20,
  "total_elements": 42,
  "total_pages": 3
}
```

Страница после последней приходит пустой (`"content": []`), это не ошибка: так фронтенд понимает, что дальше ничего нет. Того же можно добиться, сравнив `page` с `total_pages`.

**Какие списки страницами.** Только заказы: их больше всего и они растут без предела, а у склада видны заказы всех покупателей.

| Список | Страницами | Почему |
|---|---|---|
| `GET /orders` | да, `size` до 100 | растёт с каждым заказом, у склада — все заказы всех покупателей |
| `GET /orders/{id}/history` | нет | несколько записей на заказ: статусов всего пять |
| `GET /users/me/addresses` | нет | не больше 10 адресов на пользователя |
| `GET /products` | нет | каталог пока небольшой, см. [Известные ограничения](#известные-ограничения) |

**Смещение, а не курсор.** Страницы считаются через `OFFSET`: это просто и даёт номер страницы и `total_pages` для навигации «Страница 2 из 5». Цена — список может «поехать»: если пока пользователь смотрит первую страницу, появится новый заказ, все заказы сдвинутся на одну позицию, и на второй странице первым окажется заказ, который уже был последним на первой. Ничего не теряется и не ломается, просто один заказ видно дважды. Если это станет мешать (например, бесконечная прокрутка у склада), нужен курсор: `?before_id=123` и `where id < 123 order by id desc limit 20`. Он не сдвигается и не замедляется на дальних страницах, но не даёт номер страницы.

**Как пользуется фронтенд** (`lavka-web`, `app/(shop)/orders/page.tsx`): берёт по 20 заказов, внизу «← Назад · Страница 2 из 5 · заказов 87 · Вперёд →». В адресе страницы считаются с 1 (`/orders?page=2`), в запросе к API — с 0. Страница после последней перенаправляет на последнюю.

**Почему страницы и почему два запроса.** Без лимита один `GET /orders` у склада грузил бы всю таблицу заказов со всеми позициями и товарами. Сделать страницы прямо на запросе с позициями нельзя: при fetch join коллекции (`items`) Hibernate не может поставить `LIMIT` в SQL, загружает всё и режет страницу в памяти (предупреждение `HHH90003004`). Поэтому список строится двумя запросами (`OrderRepository`):

1. `select o.id ... order by id desc limit/offset` и `count(*)` — только `id` одной страницы, всё ограничение в SQL;
2. заказы с покупателем, позициями и товарами по этим `id` одним запросом (`@EntityGraph`), а не отдельным запросом на каждый заказ (N+1).

`GET /orders/{id}` загружает позиции и товары тем же запросом, что и заказ.

| Код | Когда |
|---|---|
| `200` | заказ или страница заказов |
| `400` | `page` меньше 0, `size` не от 1 до 100, `page` так велик, что смещение не помещается в `int`, параметр не число |
| `401` | нет токена или он недействителен |
| `404` | `Order {id} not found`: заказа нет или он чужой |

### Смена статуса — `PATCH /orders/{id}/status`

**Запрос:**
```http
PATCH /orders/1/status
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "status": "PROCESSING"
}
```

Разрешённые переходы:

```
CREATED ──► PROCESSING ──► READY ──► COMPLETED
   │
   └──► CANCELLED
```

| Текущий статус | Следующий статус | Разрешено |
|---|---|---|
| `CREATED` | `PROCESSING` | да |
| `CREATED` | `CANCELLED` | да |
| `PROCESSING` | `READY` | да |
| `PROCESSING` | `CANCELLED` | нет |
| `READY` | `COMPLETED` | да |
| `READY` | `CANCELLED` | нет |
| `COMPLETED` | любой | нет |
| `CANCELLED` | любой | нет |

- Вперёд можно двигаться только на один шаг, назад нельзя.
- **Отменить заказ можно только в статусе `CREATED`**, пока склад не начал его собирать. После `PROCESSING` отмена даёт `409`, и для покупателя, и для склада.
- `COMPLETED` и `CANCELLED` — конечные статусы, из них никуда нельзя.
- `completed_at` заполняется при переходе в `COMPLETED`.
- **Отмена возвращает товары на склад:** `products.quantity` увеличивается на количество из `order_items`. Вернуть их дважды нельзя, потому что `CANCELLED` — конечный статус.
- Каждая смена статуса добавляет запись в `order_status_history`.

**Ответ `200 OK`** — заказ с новым статусом.

| Код | Когда |
|---|---|
| `200` | статус изменён |
| `400` | неизвестный статус или нет поля `status` |
| `401` | нет токена или он недействителен. Проверяется раньше тела |
| `404` | `Order {id} not found`: заказа нет или он чужой |
| `403` | `Access denied`: покупатель попробовал поставить что-то кроме `CANCELLED` |
| `409` | `Can't change order status from X to Y`: переход не разрешён |

**Кто какой статус ставит:**

| Статус | Покупатель | Сотрудник склада |
|---|---|---|
| `PROCESSING`, `READY`, `COMPLETED` | нет, `403` | да |
| `CANCELLED` (только из `CREATED`) | да, только свой заказ | да, любой заказ |

Проверки идут в таком порядке: сначала виден ли заказ (`404`), потом позволяет ли роль (`403`), потом разрешён ли переход (`409`). Поэтому покупатель, который отменяет уже собирающийся заказ, получает `409`, а не `403`: отменять ему можно, но не в этом статусе.

**Где в коде.** Таблица переходов живёт в самом перечислении `OrderStatus`: метод `nextStatuses()` возвращает разрешённые следующие статусы, `canChangeTo(next)` проверяет переход. `OrderService.changeStatus` только вызывает его. Все 25 пар «текущий → следующий» проверяет модульный тест `OrderStatusTest`, без базы. В истории (`changed_by`) видно, кто именно сменил статус.

**Одновременные изменения.** Перед сменой статуса строка заказа блокируется (`SELECT ... FOR UPDATE`, `OrderRepository.findByIdForUpdate`). Покупатель блокирует заказ запросом с `user_id` в `WHERE` (`findByIdAndUserIdForUpdate`), поэтому строку чужого заказа он не блокирует и не ждёт: `404` приходит сразу, и по задержке нельзя понять, что заказ существует. Если два запроса меняют один заказ одновременно, второй ждёт, пока закоммитится первый, и читает уже новый статус. Например, покупатель дважды нажал «Отменить» или склад берёт заказ в сборку (`PROCESSING`) в ту же секунду, когда покупатель его отменяет: первый запрос получает `200`, второй — `409`. Без блокировки обе транзакции прочитали бы старый статус, обе решили бы, что переход разрешён, и отмена вернула бы товар на склад дважды. Это проверяет `OrderConcurrencyTest`: 20 раундов по 4 параллельных запроса.

### История статусов — `GET /orders/{id}/history`

**Ответ `200 OK`:**
```json
[
  { "from_status": null,         "to_status": "CREATED",    "changed_at": "2026-11-01T19:50:00Z", "changed_by": 5 },
  { "from_status": "CREATED",    "to_status": "PROCESSING", "changed_at": "2026-11-01T19:55:00Z", "changed_by": 5 },
  { "from_status": "PROCESSING", "to_status": "CANCELLED",  "changed_at": "2026-11-01T20:01:00Z", "changed_by": 5 }
]
```

| Код | Когда |
|---|---|
| `200` | история заказа |
| `401` | нет токена или он недействителен |
| `404` | `Order {id} not found`: заказа нет или он чужой |

## Известные ограничения

- **Сотрудника склада назначают только в базе.** Ручки для управления ролями нет. Если сотрудников станет много, понадобится роль администратора и ручка для неё.
- **Нет корзины.** Список покупок клиент держит у себя и присылает целиком в `POST /orders`.
- **Каталог без страниц.** `GET /products` отдаёт все товары одним ответом. Пока товаров десятки, это нормально; когда их станут тысячи, нужна такая же пагинация, как у `GET /orders`, и поиск.
- **Страницы заказов на смещении.** Новый заказ, появившийся, пока пользователь листает список, сдвигает страницы: один заказ можно увидеть дважды. Подробнее и чем заменить — в разделе [Список и один заказ](#список-и-один-заказ--get-orders-и-get-ordersid).
- **Нет возвратов.** Заказ, который начали собирать, отменить нельзя, а выполненный (`COMPLETED`) — тем более. Товар на склад вернётся только при отмене из `CREATED`.
- **Правка склада может затереть продажу.** `PUT /products/{id}` принимает абсолютный `quantity`, посчитанный от значения, которое сотрудник видел раньше. Если между его `GET` и `PUT` прошёл заказ, проданное «вернётся» на склад. Пессимистическая блокировка здесь не помогает, см. [Остатки и блокировки](#остатки-и-блокировки).
- **Брошенные заказы держат товар.** Остаток списывается при оформлении, а заказ в `CREATED`, который никто не собирает и не отменяет, держит его бесконечно. Автоотмены по времени нет.
- **Профиль `local` включён по умолчанию** (`spring.profiles.default` в `application.yaml`), пока приложение запускается только локально и в Docker. Перед выкладкой в прод это надо убрать: иначе без `SPRING_PROFILES_ACTIVE` приложение возьмёт пароль базы `lavka/lavka`, текст ошибок в ответах, `debug`-логи и открытую всем спецификацию API.
- **Отозванные токены живут в памяти** и пропадают при перезапуске. При нескольких экземплярах приложения это не работает, нужно общее хранилище, например Redis.
- **Пароль длиннее 72 байт** (например, длинный на кириллице) даёт `500`: BCrypt принимает максимум 72 байта, а проверка `@Size(max = 100)` считает символы.

## Типичный сценарий

```
register / login  ──►  access_token + refresh_token
        │
        ├─ GET /users/me            (Authorization: Bearer access_token)
        │
        ├─ POST /users/me/addresses (адрес доставки, первый становится активным)
        │
        ├─ POST /orders             (список товаров и address_id)  ──►  заказ, товары списаны, адрес скопирован
        ├─ GET /orders?page=0&size=20                        ──►  страница заказов, новые сверху
        ├─ PATCH /orders/{id}/status                         ──►  CREATED → ... → COMPLETED или CANCELLED
        │
        ├─ access_token истёк  ──►  POST /auth/refresh  ──►  новая пара
        │
        └─ POST /auth/logout        (access в заголовке + refresh в теле)  ──►  оба токена отозваны
```
